## Review Corrections Applied

This revision incorporates a correctness review of the first `tasks.md` draft. `spec.md` and `plan.md` were **not** modified — these are implementation-detail corrections and clarifications within the task breakdown, applied because the original task wording either mis-stated the plan's own intent or left a real race/ambiguity unresolved. Where a correction's literal wording differs from `plan.md`'s prose (e.g. plan §15 step 4 said "generationStatus stays whatever it was"), that divergence is called out inline at the relevant task rather than silently applied.

1. **Speak must stay clickable while `generating`** — re-clicking Speak during an in-flight round must cancel it and start a new one; the original draft's "disable Speak while generating" contradicted this and effectively made spec §7.3's regenerate-on-Speak requirement unreachable by user action. Fixed in T5.1, T6.5.
2. **Stop must reset `generationStatus` to `idle`**, not leave it at `'generating'` — the original draft (mirroring `plan.md` §15 step 4's literal wording) left the status field permanently stuck at `'generating'` after a Stop mid-generation, which misrepresents reality once the session has actually been cancelled. Fixed in T6.4.
3. **Connection reuse across Stop/cancel must not risk cross-session message leakage** — the reference message-pump does not filter `AudioOnlyServer` frames by `sessionId`, so reusing the WebSocket connection immediately after `cancelSession()` is only safe if stray frames from the just-cancelled session are reliably discarded rather than fed into the new round's player. Fixed in T3.5a (new), T3.6, T6.7.
4. **`firstChunkReady` renamed to `firstPlayableReady`, with a corrected resolution condition** — resolving on "a chunk was pushed into the JS-side queue" doesn't guarantee the `SourceBuffer` actually has a decodable, playable range yet; the signal must come from the `SourceBuffer`'s own `buffered` state after an `updateend`. Fixed in T4.2, T4.5, T4.8, T5.3.
5. **TTFA must be measured to the `<audio>` element's first `'playing'` event**, not to the `play()` call being issued or its Promise resolving — the Promise resolving doesn't guarantee audible playback has actually started. Fixed in T4.6, T5.6.
6. **Autoplay ownership consolidated entirely inside `StreamingAudioPlayer`** — `app.js` must never call `.play()`/`.pause()` on the `<audio>` element directly, and must never independently trigger the initial autoplay; it only calls the player's own public control methods and reacts to status callbacks the player emits. Fixed in T4.5, T5.2–T5.3, T6.1–T6.4.
7. **`generationStatus: 'completed'` must be gated on the provider's `SessionFinished` event**, not on the local `FinishSession` request merely being sent — `tts-client.js`'s `endSession()` must continue to await the session's `finishedPromise` (already resolved only by an observed `SessionFinished` message in the reference implementation) rather than being simplified to resolve on request-send. Fixed in T3.3, T5.2, T5.4.

- [x] **T3.3** Adapt `beginSession()` / `pushText()` / `endSession()` and the background message-pump (the `onChunk`/`onSentenceStart`/`onSentenceEnd` callback surface) — this is the core reuse this phase delivers (plan §10, §3.1). - [x] **T3.4** Adapt the low-level plumbing shared by the old and new call paths: `_sendEvent` / `_receiveMessage` / `_waitForEvent` / `_uuid` / `_voiceToResourceId()` (plan §10, reuse verbatim). **One real bug found and fixed here during verification** — see completion notes below.
- [x] **T3.5** Add the new `cancelSession()` method per plan §15's pseudocode: mark the active session cancelled, null out `_activeSession`, send `EventType.CancelSession` fire-and-forget (no await on `SessionCanceled`), and **unconditionally call `chainRelease()`** regardless of whether the send succeeds. This remains the top implementation-correctness risk (plan §3.5/§23) — `chainRelease()` must not be skipped or gated behind any success path, or every Speak after the first Stop/cancel will silently hang.
- [x] **T3.5a — Session isolation for connection reuse (review ③).** Before relying on WebSocket-connection reuse across a `cancelSession()` + fresh `beginSession()` (as plan §15 assumes for TTFA reasons), verify and, if necessary, add session isolation to the message pump: **tag every inbound message the pump reads with the `sessionId` it belongs to, and discard any `AudioOnlyServer` (or other session-scoped) frame whose `sessionId` does not match the currently active session**, rather than delivering it to `onChunk`. The existing reference pump does not do this filtering today — it dispatches `AudioOnlyServer` frames to `onChunk` purely by message type, with no `sessionId` check, which is unsafe once a connection is reused across a cancelled-then-restarted session, since a stray late frame from the old session could otherwise be misdelivered into the new round's player.
  - If this filtering can be implemented and verified reliably (see the Phase 6/T6.7 leakage test), the connection may be reused across `cancelSession()` as plan §15 intends.
  - **If reliable isolation cannot be established**, `cancelSession()` (or the next `beginSession()` call following a cancel) must instead force a full `_disconnect()` + fresh `connect()` before starting the new session, trading the TTFA benefit of connection reuse for correctness. Do not ship connection reuse across cancelled sessions without one of these two safeguards in place.
  **Outcome: the fallback was required, not the connection-reuse path** — see completion notes below. `cancelSession()` implements sessionId-tagging in the pump (defense in depth, still correct and still exercised) *and* always forces a disconnect before releasing the chain, because the real Volcengine endpoint was found — empirically, by triggering the exact race repeatedly — to leave the connection unusable server-side after a mid-flight cancel, independent of any client-side message routing.
- [x] **T3.6** Modify the background message-pump loop so it checks the session's `cancelled` flag on each iteration and exits early (supports T3.5), rather than only checking the existing 5-minute deadline. Combine this with T3.5a's `sessionId` filtering — a cancelled session's pump should stop consuming entirely, and any frame that still arrives tagged with its `sessionId` after cancellation must never reach a callback.
- [x] **T3.7** Do **not** adapt `synthesize()` / `_doSynthesize()` / `_collectAudioUntilSessionFinished()` this round (plan §10, §20) — leave them untouched in the reference source file; they are not part of Voice Copilot's code.
- [x] **T3.8** Verify via console/manual trigger (no UI wiring yet) that `onChunk` fires repeatedly for a real Speech Text against a real Voice Profile, and that `endSession()`'s Promise only resolves after the provider's `SessionFinished` is observed (log both timestamps), before treating this phase as done.

**Exit criterion (plan §24 Phase 3):** `onChunk` fires repeatedly for a real Speech Text, confirmed via console; `endSession()` resolution is confirmed to be gated on `SessionFinished`, not on request-send; session-isolation approach (T3.5a) is decided and implemented before starting Phase 4.

**Verification (2026-08-17) — real Volcengine endpoint, real credentials, actual project files (not a reimplementation):** ran the real `tts-client.js`/`volcengine-protocol.js` from Node (`node --import` with a two-line shim for the `window`/`localStorage`/`location` globals `volcengine-protocol.js`'s verbose-log IIFE touches, which exist natively in the real target — the browser — and were only missing in this ad hoc Node-based verification harness; confirmed separately via a temporary in-repo smoke-test HTML page, driven by headless Chromium, that both files import cleanly with zero console errors as real browser ES modules, then deleted before committing). Findings, in the order they were found:

1. **`onChunk` fires repeatedly for real Speech Text (T3.8, requirement 1):** confirmed — 14 chunks for a real Chinese sentence, first chunk in ~450-880ms across several runs.
2. **`endSession()` is gated on `SessionFinished`, not request-send (T3.8, requirement 2 / review ⑦):** confirmed — `endSession()`'s call-to-resolve time consistently matched the full server round-trip (~1.4-2.2s), not a near-instant request-send time.
3. **Real bug found in `_waitForEvent`'s mismatch handling, fixed:** the original (adapted-as-is) logic unshifts a non-matching message back onto the *front* of `_msgQueue` and retries. Under normal single-consumer use (the original reference code's only usage pattern) this is harmless. Once a cancelled session's pump and a new session's `_waitForEvent` call are both draining the same queue/callback structures concurrently — exactly the scenario T3.5a exists to handle — this reproducibly deadlocked: `_waitForEvent` kept re-dequeuing and re-requeuing the *same* stray message forever, never advancing to examine genuinely new incoming messages (including the `SessionStarted` it was actually waiting for) queued behind it. This is server-side, not fixable by client-side message routing. Per T3.5a's own explicit contingency for exactly this outcome, `cancelSession()` was changed to always force a full `_disconnect()` before releasing the chain (adds the disconnect/reconnect round-trip, ~150-200ms observed, to the next Speak after a Stop — an accepted, documented tradeoff, not a regression). Re-ran the cancel-mid-flight-then-restart scenario 5 consecutive times after this change: 5/5 succeeded cleanly with the correct sessionId isolation and zero cross-session chunk leakage into the new round's `onChunk`, versus 3/4 hangs before it.

Both fixes are in the committed `tts-client.js`, not left as follow-up work — Phase 3's exit criterion would not otherwise be honestly satisfied ("session-isolation approach is decided and implemented"). ## Phase 4 — Streaming Audio Player ✅ Done

Files: `js/streaming-audio-player.js`

- [x] **T4.1** Adapt the `StreamingAudioSource` constructor (`<audio>` element + `MediaSource` + Object URL) from `public/js/streaming-response-handler.js` into `streaming-audio-player.js`, **dropping `setupAnalyser()` entirely** — it is 100% Live2D lip-sync-specific and not called by anything else in the class (plan §15, §3.2). This class is the **sole owner** of the `<audio>` element for the lifetime of a Speak round (review ⑥) — no other module may call `.play()`, `.pause()`, or set `.currentTime` on it directly.
- [x] **T4.2** Adapt `appendChunk()` / `_flush()`: queue-and-append incoming bytes into the `SourceBuffer`.
  **Correction (review ④ — `firstPlayableReady`, not `firstChunkReady`):** do **not** resolve the "ready to play" signal simply because the first chunk was pushed into the internal JS queue or handed to `appendBuffer()`. Instead, expose a `firstPlayableReady` promise that resolves only after the `SourceBuffer`'s `updateend` event has fired for an append **and** `sourceBuffer.buffered.length > 0` with a non-zero duration — i.e., only once the browser itself confirms there is an actual decodable, playable range, not just "some bytes were submitted." A single very small first chunk may not be enough to form a playable range on its own; keep checking on subsequent `updateend` events until `buffered` actually reflects playable content.
- [x] **T4.3** Adapt `end()` (marks the stream ended; the existing `_flush()` logic eventually calls `mediaSource.endOfStream()` once the queue drains) and `dispose()` (pause, detach `src`, revoke Object URL) (plan §15). `end()` is called by `app.js` only after Phase 3's corrected `endSession()` has resolved (review ⑦) — never earlier.
- [x] **T4.4** Explicitly do **not** build the reference implementation's `_audioQueue`/`_playLoop` FIFO — Voice Copilot instantiates exactly one player per Speak round, never more than one active source at a time (plan §3.3, §15).
- [x] **T4.5** Implement the playback orchestration, fully owned inside this class (review ⑥): `await firstPlayableReady` → the player itself calls `audio.play()` internally, with no external trigger required. On success, the player updates its own `playbackStatus` to `'playing'` and invokes an `onPlaying` callback (used for TTFA, see T4.6/T5.6). On `NotAllowedError` rejection, the player invokes an `onAutoplayBlocked` callback so the caller can show the manual-Play affordance (Phase 5) — the player does not treat this as `playbackError`. Expose public control methods `pause()`, `resume()`, `replay()`, `stop()` (each internally calling the corresponding `<audio>` operation) as the **only** way any other module may affect playback — `app.js` must never reach into the `<audio>` element directly (review ⑥; see also T6.1–T6.4). (Also added an `onStatusChange` callback, not explicitly named in the plan but required to actually wire review ⑥'s "app.js reacts to the player's callbacks" design in Phase 5/6 — no other task owns defining this surface.)
- [x] **T4.6** Implement the `'playing'`, `'ended'`, `'pause'`, and `'error'` listeners on the `<audio>` element, all internal to the player:
  - `'playing'` (first occurrence per round) → fire the `onPlaying` callback used for TTFA (review ⑤ — this, not the `play()` call or its Promise resolving, is the signal that audio is actually audible) and update `playbackStatus: 'playing'`.
  - `'ended'` → `playbackStatus: 'stopped'` (natural completion).
  - `'error'` → `playbackError` set via an `onError` callback (plan §8's dedicated playback-error slot).
  **Implementation note found while building this:** the native `'pause'` event fires asynchronously for *both* a user Pause and a Stop's `audio.pause()` call, so a naive listener would race with `stop()`'s own explicit `'stopped'` status write and sometimes clobber it back to `'paused'`. Fixed with a small `_suppressPauseEvent` guard set around `stop()`'s own `pause()` call — not a deviation from the task, just a concrete detail the task description didn't need to spell out.
- [x] **T4.7** Implement the 250ms watchdog adapted from the reference implementation: once the stream has ended, poll `audio.buffered`'s end against `currentTime` to catch cases where `MediaSource.endOfStream()` doesn't reliably fire `'ended'` (plan §15).
- [x] **T4.8** Verify in isolation (e.g. feeding manually-captured or test chunks, no live TTS session required) that `firstPlayableReady` only resolves once `buffered` actually shows a playable range (not merely on the first `appendChunk()` call), and that playback starts before all chunks have arrived.

**Exit criterion (plan §24 Phase 4):** player starts audio well before all chunks have arrived, confirmed in isolation, with `firstPlayableReady` verified against real `buffered` state rather than queue-push timing; all `<audio>` control is confirmed to live exclusively inside this file, before starting Phase 5.

1. **Stop did not actually cancel generation at all.** Root cause: `endSession()` (called immediately by `handleSpeak()` right after `pushText()`, not waiting for user interaction) nulled `this._activeSession` synchronously on entry, while still genuinely awaiting the real `SessionFinished`. By the time a later Stop click called `cancelSession()`, `_activeSession` was already `null` — `cancelSession()` found nothing to act on, silently no-op'd, and critically never called `chainRelease()`. The UI still showed `idle` (set unconditionally by `teardownCurrentRound()`, correct per review ②), but the *old* generation kept running server-side underneath, and the next Speak's `beginSession()` sat blocked on the chain until that old session's real `SessionFinished` eventually arrived — up to 15+ seconds later for a long text, not a hang exactly, but a silent, severe violation of spec §7.1 ("终止当前 TTS Streaming Session"). Fixed: `endSession()` now only clears `_activeSession` in its `finally` (keyed off object identity), keeping the session visible to a concurrently-issued `cancelSession()`, which now settles the shared `finishedPromise` itself (the pump's own cancelled-early-return never does) so a concurrently in-flight `endSession()` unblocks instead of waiting on a `SessionFinished` that will never come.
2. **The first fix introduced a second real bug**, caught by re-running the same reproduction immediately after: resolving `finishedPromise` *before* `cancelSession()`'s forced disconnect (Phase 3, T3.5a) completed let the concurrently-unblocked `endSession()` release the chain early, letting the *next* `beginSession()`'s `connect()` race the still-in-progress teardown of `this.ws` — reproduced as `Cannot set properties of null (setting 'onmessage')`. Fixed by moving the `finishedResolve()`/`chainRelease()` calls to the end of `cancelSession()`, strictly after the disconnect finishes.
